# Native app decisions and feature parity roadmap

## Goal and sources of truth

Build the React Native app to full feature parity with the existing web app. Users should recognize the same Movies product on either platform: familiar branding, content, terminology, information hierarchy, colors, artwork, ratings and actions. Native navigation and interaction should feel at home on iOS and Android.

This is an incremental rewrite, not a requirement to port every API procedure up front. Complete one user-visible slice at a time and port only the operations it needs. The first slice is the homepage. The current native homepage is a functional foundation, **not the visual parity target**; it needs a deliberate comparison with the web design before its presentation is considered complete.

## Visual recognition rule

Native screens must look substantially closer to their web counterparts than the current native homepage does. Inspect the web screen before implementing or restyling its native version. Preserve the recognizable brand mark, movie/TV accent distinction, content order, card treatments, backdrop overlays, poster proportions, title/year/rating hierarchy, wording and primary actions. Adapt spacing and touch targets to the device; do not replace the product's design with a generic mobile template.

Use native stacks/tabs or appropriate native navigation, platform back buttons and gestures, native sheets, menus and pickers where they improve the interaction. Translate web hover-only affordances into visible, accessible touch actions rather than dropping them. Do not reproduce a desktop sidebar or browser history controls merely to match markup. Recognition concerns the product's appearance and workflows, not shared DOM or identical screen geometry.

For each screen, compare web and native side by side with the same records, region, session and theme. Check light/dark appearance, small phones, larger screens, long titles, missing artwork, loading, empty and error states. Explain any intentional platform difference in the slice's PR. The reference repo informs implementation mechanics; it does not replace this visual comparison.

## Engineering standards

- Use clean code and senior engineering patterns: cohesive modules, descriptive names, small interfaces, explicit contracts, and clear separation of presentation, transport and server operations. Keep one canonical implementation of each shared rule.
- Prefer straightforward functions and explicit control flow. Do not overuse ternaries, nested conditional expressions, boolean short-circuit chains or dense transformation chains. Break meaningful decisions into named helpers, intermediate values and ordinary `if`/`return` blocks. A short ternary is acceptable when it is the clearest expression of a simple choice; avoid nesting them.
- Helpers should explain a domain or UI rule and reduce the reader's cognitive load. Do not replace a dense expression with a stack of one-line forwarding wrappers, speculative abstractions or unnecessary configuration flags.
- Validate inputs at the interface, keep authorization explicit, and make loading/error/empty behavior reviewable. Do not hide failures in empty catch handlers. Keep transactions and cache refresh behavior visible at the appropriate server interface.
- Keep changes reviewable by completing small vertical slices with meaningful contract and workflow tests. Preserve behavior during extraction, and document intentional changes and remaining limitations.

## Data and cache safeguards

- Share contracts and framework-independent rules; keep native presentation separate from the DOM/Base UI package.
- Extract operations from web actions into their canonical server modules as needed. Keep ownership checks, anonymous-account semantics, transactions and validations intact; do not merely wrap an imported Next action in oRPC.
- API mutations must refresh the appropriate native queries and have a tested mechanism for web cache freshness. A standalone Hono process cannot assume it can call the web process's Next cache invalidation functions.
- Preserve the shared PostgreSQL title/provider/search/IMDb data and existing cron schedules. Do not create duplicate jobs for the app or change infrastructure topology as incidental porting work.
- Keep secrets and database access out of client bundles. Keep database/client-specific fields out of transport contracts unless deliberately part of the contract.
- Port needed calls now, retain a single contract for future clients, and test error/authorization behavior alongside successful requests.

## Verification and progress tracking

For each slice, record implemented workflows, visual comparison evidence, API calls moved, tests run and outstanding device/platform checks. Run `pnpm lint`, `pnpm exec tsc --noEmit`, `pnpm check-types`, `pnpm test` and `pnpm fallow`. Run native browser tests and native bundles when app code or bundler/env integration changes; use real device or simulator checks for native navigation, session storage, gestures and platform UI.

The current automated baseline verifies the homepage, region changes, native movie/TV routes and deep links, same-document back navigation with region/scroll restoration, core metadata, loading/optional-data/not-found states, error/retry/empty states, Tailwind image sizing and system theme changes. API tests cover contract/transport behavior, category dispatch and upcoming filtering. Env validation should read the actual tracked schemas in isolated fixtures or startup checks, not maintain a second hand-written schema just for tests. A successful bundle is not a successful phone session; report those separately.
