# Shared product API

Both apps import domain query and mutation hooks directly from `@movies/api/react/use-<domain>-query`. The shared hooks own contract inputs, query keys, enabled guards, pagination placeholders, mutation invalidation and retry policies. Screens own rendering, URL/navigation state and form drafts. Mutation hooks own pending state and account invalidation; components must not recreate query-key factories or invalidate obsolete keys. Avoid forwarding modules in the app folders.

`ApiProvider` supplies query utilities and account identity. Web calls the same-origin `/api/rpc` route with its existing cookies. Native calls Hono's `/rpc` endpoint with its existing authenticated transport. Only `apps/server` executes `@movies/api/router` and `@movies/services`. Web's route forwards cookies and request bytes to Hono; server components, metadata readers and prefetches use an HTTP oRPC client pointed at the same service. No product execution fallback exists in Next.

The shared domains are home, catalog (including credits, providers, reviews, images, trailers, seasons, collections and IMDb), person, search, discovery/facets, preferences, custom lists and system lists. Better Auth and passkeys retain their browser/native SDK adapters and platform-specific hooks.

Next server components cannot call React Query hooks. They call Hono over HTTP through `createServerApi`, then prefetch with `createApiQueryUtils` where the client resumes the query. All server-only catalog presentation readers also call the router, including full movie/TV/person metadata, cast and crew, all regional watch offers, reviews, IMDb ratings, external IDs and IMDb redirects. Validated full metadata contracts preserve rich detail-page fields alongside the smaller card/native projections. The web adapters own only Next cache tags/lifetimes and presentation. Public presentation reads retain Next's cache; Hono caches successful upstream responses and evicts failures before optional fallbacks are applied. Private service reads always resolve the verified session. Successful mutations emit typed domain events from the router after input validation and execution. Hono delivers those events to `/api/internal/invalidate` on web, authenticated with a timestamped HMAC over the exact body using the shared auth proxy secret. Next validates the event and immediately expires account tags and revalidates paths. Browser and native mutations both await delivery attempts; failed writes never send events. Delivery retries transient errors three times. Exhausted delivery is logged with the validated event, and a committed write still returns success so clients do not repeat it. No durable outbox is provided: during a prolonged callback outage, existing open-client navigation data can remain stale until its normal freshness window expires. Signed events can be replayed within the 30-second clock window; this only repeats an idempotent invalidation. Next presentation caches retain their existing lifetimes and tags. Hono owns a bounded process-local cache for successful public TMDB reads (one minute) and Wikidata claims (one day); failures are evicted.

Private keys start with `['account', accountId]`. A managed signed-out provider disables private reads; native adapters can supply their current identity explicitly. Mutation invalidation captures the submitting identity, so a late response cannot refresh a replacement account's cache. Private hooks switch cache identities with the session; native's session boundary also resets its caches on account changes.

Regression coverage includes router authorization/input validation, shared service behavior, server-prefetch hydration, signed-out/account-switch isolation, late mutations, and Next's RPC/cache-invalidation boundary. Former web server-action wrapper tests were replaced by these common service and transport boundaries rather than retaining a second implementation.

Offline IMDb/search-index ingestion helpers live in `@movies/db`, and SQL/hydration tests sit with their canonical implementations. These maintenance jobs do not execute in web requests. The web request layer accesses the database only through the API host, Better Auth and startup connection checks; product upstream fetches are confined to Hono. Better Auth is hosted by Hono from the shared `@movies/auth` package.

Web cards consume the canonical `MediaCard` and `SearchPersonCard` models. Raw filmography fields are normalized by the server presentation boundary; cards do not accept legacy TMDB unions. Signed image sources are a separate optional rendering prop.

List reordering requires a complete, unfiltered result for the current page. Previous-data placeholders may keep content visible, but cannot canonicalize the URL or enable moves. Both web list types use the returned page for position offsets and block moves when hydration reports unavailable titles.

## Runtime configuration and freshness

Web's per-app Varlock `API_URL` points at the Hono origin (development default `http://localhost:3001`; production requires an explicit origin). Native keeps `EXPO_PUBLIC_SERVER_URL`. Like Better T Stack, `@movies/auth` exports `createAuth(config, database)` and inferred `Auth`/`Session` types. Hono creates one instance, mounts `auth.handler()` at `/api/auth/*`, and verifies private RPCs locally with `auth.api.getSession({ headers, query: { disableCookieCache: true } })`. Better Auth owns token validation and expiry; no session verification calls return to Next.js.

Web keeps `/api/auth/*` as a same-origin HTTP proxy to Hono. This preserves host-only browser cookies, configured OAuth callback URLs and the existing passkey relying-party domain. Its React client and native's Expo/SecureStore client use the official Better Auth SDKs. Server components and passkey settings use the official server-side client against Hono with forwarded request cookies and no response caching. Public browser auth endpoints retain Better Auth origin/CSRF checks. The product proxy supports only POST, including reads, so GET cannot execute writes; user IDs and identity headers supplied by clients never establish ownership.

Hono uses `BETTER_AUTH_URL` for the **public web origin**, `BETTER_AUTH_SECRET` for the existing session signing key, the same `DATABASE_URL`, OAuth credentials, and `PASSKEY_ANDROID_FINGERPRINTS` matching web's public association endpoint. Web no longer loads OAuth credentials or instantiates Better Auth. `AUTH_PROXY_SECRET` on Hono must match web's `BETTER_AUTH_SECRET` for signed ingress metadata and cache events. The web signing-key variable keeps its old name to preserve existing deployment references; it is not a second auth instance. The proxy signs original IP metadata only with `RPC_IP_SOURCE=railway`. Hono validates the signature/method/path, otherwise uses its trusted socket/Railway ingress IP, and strips caller-selected forwarding headers before Better Auth sees them. Native auth goes straight to Hono. `WEB_URL` is the internal Next cache invalidation destination.

### Migrating the auth host

1. Configure Hono's `BETTER_AUTH_URL` with the existing `NEXT_PUBLIC_BASE_URL`, **not** its private API URL. Keep the existing database and signing secret so issued sessions remain valid. OAuth callbacks remain `<web-origin>/api/auth/callback/<provider>` and passkeys retain their RP ID.
2. Move Discord/GitHub credentials and the trusted origin to the server environment; copy Android fingerprints to the server while keeping them on web for the association document. Local values are documented in `apps/server/.env.example`. Varlock requires the database and auth credentials whenever auth is enabled, and all production instances require auth configuration.
3. Deploy the new Hono auth host first, then switch web to this version. The old API forwards auth to web; the new web forwards auth to API, so mixing those two versions would create a proxy loop. The checked-in Railway config references existing web credentials from the API and retains them on web as migration sources; remove those stored web OAuth variables only after moving the references to independently managed API values.
4. Verify anonymous sign-in, existing session reads, sign-out/revocation, social callbacks, passkey sign-in/registration and anonymous-account linking on the preview. Unit tests cover the shared factory, real Better Auth HTTP/RPC revocation, passkey RP options, proxy headers/cookies/redirects and rate limiting; provider callbacks and native device flows still require configured providers/devices.
